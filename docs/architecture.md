# Architecture

## Overview

A single-user, self-hosted investment intelligence platform. Three processes
share one Postgres database; a React SPA talks to the API via Vite proxy in
dev and Caddy reverse proxy in production.

```
Browser (React SPA)
      │  /api/*
      ▼
  Caddy :80/:443  ──────────────────────────────────────────┐
      │ /api/*                           static /srv/web    │
      ▼                                                      │
  FastAPI :8000   ←──── PostgreSQL :5432 ────→  APScheduler Worker
      │                     (single DB)
      ▼
Tiingo / CoinGecko / other providers (outbound only)
```

---

## Processes

| Process | Tech | Role |
|---------|------|------|
| `api` | FastAPI + SQLAlchemy async | REST endpoints consumed by the SPA |
| `worker` | APScheduler (background) | Periodic ingestion, recommendation runs, alert dispatch |
| `db` | PostgreSQL 17 | Source of truth for all data |
| `web` (dev) | Vite 5 | Dev server + proxy; replaced by Caddy-served static build in prod |

---

## Database

Schema families:

- **Ledger** — `transaction`, `lot`, `position_snapshot` (see `docs/ledger-model.md`)
- **Market data** — `symbol`, `price_bar`, `fundamental_snapshot`
- **Signals & recs** — `signal`, `recommendation` (5-action enum + metadata)
- **Briefing** — `briefing` (daily text blobs generated by the worker)
- **Alerts** — `alert_rule`, `alert_event`
- **Jobs** — `job_run` (heartbeat + last-error per job)

Migrations managed by Alembic. Run `alembic upgrade head` before first use.

---

## Ingestion Pipeline

1. Worker job fires on schedule (cron expression in APScheduler).
2. Fetches from provider (Tiingo EOD, Tiingo IEX, CoinGecko free tier).
3. Upserts `price_bar` rows; updates `fundamental_snapshot` on relevant schedule.
4. Writes `job_run` record (status, duration, error).
5. Marks affected `symbol` rows with `data_freshness` timestamp.

Rate limits are enforced client-side (token bucket per provider). See
`docs/data-providers.md`.

---

## Recommendation Engine

Runs after each successful ingestion batch. See `docs/recommendation-engine.md`
for the full spec.

1. Load `engine.yaml` weights at startup.
2. Compute signals per symbol (valuation, trend/momentum, volatility/risk,
   macro regime, exposure).
3. Apply `enough_data` thresholds — symbols with insufficient history are
   skipped rather than scored.
4. Emit `recommendation` row (action ∈ {STRONG_BUY, BUY, HOLD, REDUCE, SELL},
   confidence, tags[], engine_version).
5. Recommendations are reproducible — same inputs + same `engine.yaml` =
   same output.

---

## Alerts

Alert rules are stored in `alert_rule` (price threshold, freshness SLA breach,
recommendation change). The worker evaluates rules after each ingestion run and
writes `alert_event` rows. Delivery channels (email, webhook) are configured
in Settings.

---

## Options — Deferred

Options data (Greeks, IV surface) is intentionally out of scope for Phase 0.
The schema includes a `derivative_type` column on `symbol` reserved for future
use. Engine weights for options-specific signals are commented out in
`engine.yaml`.

---

## Freshness Model

Every data entity has a `fetched_at` timestamp. The `FreshnessBadge` component
classifies data as:

| Status | Condition |
|--------|-----------|
| `fresh` | `fetched_at` within the job's SLA window |
| `stale` | Beyond SLA but not errored |
| `failed` | Last job run ended in error |

SLA windows are defined per-symbol-type (equity EOD: 26 h, crypto: 2 h,
fundamentals: 7 d).

---

## Security

- All secrets (DB password, API keys, Fernet key) are in `.env` — never
  committed.
- Fernet encryption wraps any third-party API keys stored in the DB.
- The API has no auth layer in Phase 0 — it binds to `127.0.0.1` only.
  Add HTTP Basic Auth or a token gate before exposing to a network.
- Postgres port is bound to `127.0.0.1:5432` in dev compose.
- In prod, Caddy terminates TLS; Postgres is not exposed.
